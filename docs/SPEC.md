# 1. Instructions to the Coding Agent

Build a production-minded MVP for a mobile social network centered on Jacksonville, Florida. The product combines a general local discussion feed with separate discussion rooms for public-facing businesses and places.

The application should support pseudonymous participation, location-based access controls, community moderation, and a pre-populated business directory.

**Implementation rules:**

1. Inspect the existing repository before making changes. If no repository exists, initialize a clean project.
2. Implement the application in small, verifiable phases. Do not attempt to generate the entire system in one unreviewable change.
3. Prioritize working end-to-end functionality over placeholders, mock data, and excessive abstractions.
4. Never trust client-provided GPS coordinates, account roles, vote counts, moderation status, or account ownership without server-side validation.
5. Never commit secrets, API keys, database passwords, or production credentials.
6. Do not silently omit features. If a requirement cannot be implemented because an external service, credential, or data source is unavailable, document the dependency and provide a clear integration point.
7. Add database migrations, automated tests, seed scripts, setup documentation, and environment-variable examples.
8. Do not deploy publicly, incur paid-service charges, or create production infrastructure without authorization.
9. Ask for clarification only when a genuine blocker exists. Use the defaults in this specification for other decisions.
10. Do not claim a feature is complete until its main behavior and relevant security checks have been implemented and tested.

# 2. Product Overview

The application is a location-based social network for people physically visiting or spending time in Jacksonville. Users participate through unique usernames rather than publicly displayed real names.

The product has two foundational discussion experiences:

**A. General local feed**

A location-based feed for conversations about the surrounding area. It is not associated with an individual business. Examples include neighborhood conversations, local recommendations, questions, and community observations.

**B. Business and place discussions**

A separate directory of public-facing businesses and places. Selecting a location opens a dedicated discussion room for that specific place.

Examples include restaurants, coffee shops, bars, parks, retail stores, and auto dealerships. Exclude office-only buildings and businesses without a meaningful public-facing destination.

The two experiences must remain separate in the interface, database relationships, location validation, and content queries.

The product should be designed to support future features such as following users, direct messaging, events, meetups, and sponsored business content. These are not required for the initial release.

# 3. Technology Stack

Use the following stack unless an existing repository contains a compelling reason to retain a compatible alternative.

- **Mobile application:** React Native, Expo, and TypeScript.
- **Navigation and client state:** Expo Router and a lightweight state-management approach.
- **Backend API:** TypeScript using Next.js API routes or a similarly maintainable server framework. Choose one approach and document the rationale; do not create redundant backend services.
- **Administration portal:** Next.js web application, responsive for desktop and mobile browsers.
- **Database:** PostgreSQL with PostGIS for geographic queries.
- **ORM:** Prisma for standard database operations; use parameterized raw SQL where PostGIS functionality requires it.
- **Image storage:** Private S3-compatible object storage with short-lived, authorized access to uploaded images.
- **Authentication:** Secure server-managed sessions or a well-maintained authentication library appropriate for the chosen architecture.
- **Testing:** Unit, integration, authorization, and end-to-end tests for critical workflows.

Redis, dedicated background workers, push notifications, and other infrastructure should be introduced only when required by an actual feature or operational limitation.

Do not use local device storage as the authoritative source for authorization, user identity, moderation status, or location eligibility.

# 4. User Accounts and Pseudonymous Identity

## 4.1 Registered accounts

Registration must require:

- A unique username.
- An email address.
- A password or an appropriately secured alternative authentication method.
- Birth year for age eligibility.
- Acceptance of the Terms of Service.
- Explicit confirmation that the user meets the minimum age requirement.

Email addresses must never appear on public profiles or be exposed through public APIs.

Passwords must be hashed using a modern password-hashing algorithm through a reputable library. Implement secure session handling, login throttling, and appropriate password-reset protections.

Do not require a legal name, government ID, or phone number for ordinary registration.

## 4.2 Age eligibility

The application is restricted to adults aged 18 and older.

Collect birth year only, not a full date of birth. Keep it private and separate from public profile information.

Because birth year cannot determine exact age throughout the year, use a conservative eligibility cutoff: initially, users must have a birth year no later than the current year minus 19. In 2026, that means 2007 or earlier.

This deliberately excludes some people who are already 18. Make the cutoff configurable and test it at year boundaries.

Explain that the app is 18+ and that birth year is collected for age eligibility. Do not expose it publicly or imply that it is not stored.

This is a limited age screen, not proof of exact age. Document the limitation and do not describe the system as verified identity or definitive age verification.

## 4.3 Usernames and profiles

Each registered user receives an internal immutable user ID.

Public profiles may contain:

- Username.
- Optional avatar.
- Optional biography.
- Earned medals and achievements.
- Public posts and comments, subject to moderation and deletion policies.

Users may change usernames subject to a configurable cooldown and availability check. Username changes must not create a new identity or bypass prior bans and moderation history.

Optional demographic information is not needed for the MVP. Do not collect race, ethnicity, gender, or other sensitive profile attributes unless a later, justified feature requires them and appropriate privacy protections are established.

## 4.4 Account deletion

Support account deletion through account settings.

Deletion should immediately disable login and posting, remove the account from public profile views, and mark the account as deleted in the database.

Use fields such as `is_deleted` and `deleted_at`, alongside an explicit data-retention policy.

Do not permanently retain all account data indefinitely. Separate data needed for security and moderation from data that should be erased. Administrators may permanently purge eligible accounts, subject to documented retention obligations.

# 5. Guest Accounts

Guests provide a lower-friction way to participate without registering an email address.

Guest capabilities:

- Browse the general discussion feed.
- Comment on general discussions.
- Receive a persistent internal guest identifier for abuse prevention.
- View their limited guest interface and account status.

Guest restrictions:

- Cannot create top-level posts.
- Cannot participate in business discussion rooms.
- Cannot upload photos.
- Cannot send private messages.
- Cannot earn trophies, achievements, or medals.
- Cannot bypass location checks, reporting, rate limits, or moderation.
- Cannot use guest status to evade an existing ban.

Give guests a visible, distinctive **GUEST** identifier next to their posts and comments. Use a consistent neutral presentation rather than exposing a real identity.

## 5.1 Guest expiration

Expire guest accounts after 30 days of inactivity.

When practical, warn guests before expiration. Inactivity and expiration must be calculated server-side.

Guest comments should remain visible for one year from creation, including after guest-account expiration, unless removed for policy violations or other legitimate reasons.

Preserve the guest label after expiration. Do not expose an expired guest's internal identifier publicly.

Retain only the internal records needed for moderation, security, and enforcement for defined periods. An expired guest should not become an untraceable route around a ban.

Document the expiration, deletion, and content-retention policies in the application.

# 6. Location and Jacksonville Eligibility

Location is a core security and product requirement, not just a feed-filtering preference.

## 6.1 Jacksonville boundary

Obtain a reliable polygon representing the relevant City of Jacksonville consolidated municipal boundary. Record the authoritative data source, version, and any applicable usage or attribution requirements.

Store the polygon in PostGIS and perform point-in-polygon checks on the server.

Do not substitute a simple city-center radius for the municipal boundary.

Users may register from anywhere. However, location-restricted participation is permitted only when the server determines that the user is physically within the supported Jacksonville area and meets the relevant discussion's proximity requirements.

Users outside the eligible area may access their account, profile, settings, and permitted read-only browsing experiences. They cannot post, comment, vote, upload, or otherwise interact with location-restricted content.

## 6.2 Location permission and validation

Request foreground location permission when a user attempts to use location-dependent features. Explain why the permission is needed.

For restricted actions, the client submits a fresh location reading and relevant device-provided accuracy information to the server.

The server must independently validate:

- The user is authenticated or has a valid guest session.
- The location reading is sufficiently recent.
- The reported point is inside the Jacksonville boundary.
- The point satisfies the applicable discussion radius.
- The reading meets a configurable accuracy threshold.
- The account is not suspended, banned, deleted, or otherwise ineligible.
- The requested action is authorized for that account type.

Client-side checks may improve usability but cannot authorize an action by themselves.

Do not claim GPS spoofing can be completely prevented. Implement reasonable anti-abuse measures, such as anomaly detection, action throttling, device/app integrity signals where available, and temporary restrictions when location data appears suspicious.

Do not collect hardware MAC addresses. Mobile applications generally cannot read a device's real hardware MAC address. If needed, use a privacy-conscious, server-issued installation identifier and platform-supported integrity mechanisms. Do not treat these as infallible unique-device identifiers.

## 6.3 Location privacy

Do not publicly display a user's exact coordinates, device location history, or precise posting coordinates.

Store only the geographic precision needed for nearby content discovery, location enforcement, and abuse investigation.

Restrict access to sensitive location records. Define a retention period and delete unnecessary location telemetry.

# 7. Radius and Feed Behavior

Provide separate radius settings for general discussions and business discussions.

Initial configuration:

| Setting | Default | Minimum | Maximum |
|---|---:|---:|---:|
| General discussion radius | 1 mile | 0.25 mile | 1 mile |
| Business discussion radius | 0.3 mile | 0.1 mile | 0.3 mile |

Users may narrow their radius but cannot expand it beyond the configured maximum. Store defaults and limits in server-side configuration.

Convert miles to meters consistently for spatial queries.

## 7.1 General feed

The general feed is the default landing screen.

Show relevant nearby discussions based on the user's permitted viewing radius and the geographic area associated with each discussion.

A new top-level post must be associated with a validated location at creation time. The server determines its geographic association rather than trusting arbitrary coordinates supplied by the client.

Before creating a post or comment, verify the author is physically within the permitted radius of the relevant discussion area.

## 7.2 Business discussions

Every business discussion is associated with one canonical business/place record.

For posting, commenting, voting, and uploading in a business room, the user must satisfy the business proximity requirement using a fresh, validated location reading.

The business radius defaults to 0.3 mile and cannot exceed the configured maximum.

## 7.3 Read-only browsing

Allow permitted read-only browsing outside a user's current eligible radius. Browsing does not grant permission to interact.

The server must enforce action permissions separately for every write endpoint. Hiding a button is not sufficient.

# 8. General Discussion Features

The general feed must support:

- Text posts.
- Photo attachments for eligible registered accounts.
- Comments and replies.
- Upvotes and downvotes.
- Username links to public profiles.
- Reporting and blocking.
- Chronological and basic relevance-based sorting, where practical.
- Pagination or cursor-based loading.

The feed must be independent of business discussion rooms.

Posts and comments should show timestamps and the author's username or GUEST identifier. Do not expose private account data.

Implement votes using a database constraint that prevents duplicate votes of the same type by the same user on the same item. Changing a vote should update the existing vote rather than creating another record.

Use server-calculated vote totals. Clients must never submit authoritative vote counts.

# 9. Business and Place Directory

## 9.1 Initial dataset

Pre-populate the directory using a legitimate source such as OpenStreetMap, subject to its licensing and attribution requirements.

Each place record should support:

- Internal place ID.
- Source identifier and source name.
- Name.
- Category.
- Address, where available.
- Latitude and longitude.
- Geographic point.
- Active/inactive status.
- Source attribution.
- Creation and last-updated timestamps.

Use source IDs and geographic proximity to identify duplicates.

Do not attempt to import every building or office in Jacksonville indiscriminately. Filter the initial dataset toward public-facing destinations.

The data import must be repeatable and idempotent so running it twice does not create duplicate records.

Document how to update or refresh the dataset.

## 9.2 Finding a place

Provide a searchable directory and nearby-place results.

Users can favorite locations. Favorited places should appear prominently in the user's location search results without replacing geographic relevance entirely.

The location selection flow must distinguish between the general feed and an individual business room.

## 9.3 Community-submitted locations

Allow eligible registered users to suggest missing public-facing places.

A submission includes:

- Business/place name.
- Category.
- Address or selected map point.
- Optional supporting notes.
- Submitter ID.
- Submission timestamp.

Before accepting a submission:

1. Search for matching names and nearby existing locations.
2. Detect likely duplicates using normalized names, source IDs, and geographic proximity.
3. Validate that the submitted location falls within the supported Jacksonville boundary.
4. Apply per-account and risk-based submission limits.
5. Reject or flag obviously invalid entries.

New submissions must enter a moderation queue. They must not automatically become publicly searchable or receive a contributor badge.

Upon approval, create or activate the canonical location record and award the submitter the designated approved-contributor badge.

Rejected submissions should retain a reason for internal review and allow resubmission or correction where appropriate.

# 10. Administration Portal

The admin portal is a required MVP component. It should be a separate web-based experience, not a hidden public-app screen.

Prioritize usability and operational efficiency. A single administrator should be able to review a large batch of business submissions and reports without opening every item individually.

## 10.1 Authentication and authorization

- Require a separate administrator role and explicit server-side authorization.
- Never grant admin access based on a client-side role field.
- Protect administrative routes and API endpoints.
- Support secure administrator sessions and stronger authentication where available.
- Log sensitive administrative actions.
- Do not include administrative secrets in the mobile app.

## 10.2 Business submission queue

Provide a dedicated queue with:

- Pending, approved, rejected, and duplicate/merged states.
- Search and filters by status, category, submitter, and date.
- Business name, category, address, map preview, and duplicate candidates.
- Submitter history and previous submission outcomes.
- Quick approve and reject actions.
- A rejection-reason field.
- Ability to correct metadata or merge a submission into an existing canonical place.
- Clear confirmation before irreversible or consequential actions.
- A history of decisions and administrator identity.

Support selecting multiple submissions for bulk review or approval when safe. Do not make it easy to bulk-approve unverified locations without reviewing their details.

Prevent duplicate submissions from producing multiple badges or duplicate place records.

## 10.3 Moderation dashboard

Provide queues for reported posts, comments, profiles, images, and business submissions.

Administrators must be able to:

- Review reported content and relevant context.
- Remove or restore content.
- Warn, suspend, or ban users.
- Review prior violations.
- Inspect appeal requests.
- Apply or adjust rate limits.
- View the reason and history for moderation decisions.
- Record internal notes.
- Review suspicious location activity when justified.
- View audit logs for consequential actions.

All moderation decisions should have a reason, timestamp, acting administrator, and target record.

# 11. Content Moderation and Community Safety

The goal is strong, consistent moderation without suppressing ordinary disagreement or harmless profanity.

## 11.1 Content rules

Prohibit, at minimum:

- Credible threats and encouragement of violence.
- Doxxing and unauthorized disclosure of sensitive personal information.
- Targeted harassment and stalking.
- Nonconsensual intimate imagery.
- Child sexual abuse material.
- Spam, scams, impersonation, and malicious links.
- Attempts to evade bans or disrupt the platform.
- Other clearly unlawful or expressly prohibited content.

Ordinary profanity and controversial opinions should not automatically result in punishment.

## 11.2 Text screening

Implement configurable screening for slurs, threats, and other prohibited language.

Use normalization to detect common obfuscations and spelling variants. Keep the rules configurable so the moderation list can be updated without rewriting core application logic.

When a user attempts to submit content that appears to violate a rule, provide an explanatory prompt where practical.

Do not permanently ban users solely because an automated classifier flags content. Use context, confidence, report history, and human review for consequential enforcement decisions.

High-risk content may be blocked or held for review according to explicit rules.

## 11.3 Reports, blocks, and enforcement

Users must be able to report posts, comments, profiles, and images, and block other users.

Implement:

- Configurable daily posting and commenting limits.
- Per-minute and burst rate limits.
- Guest-specific restrictions.
- Duplicate-content and spam detection.
- An escalating strike system.
- Temporary suspensions.
- Permanent bans.
- Appeals or unban requests under configurable eligibility rules.
- Persistent internal enforcement history across username changes.

Do not reward raw posting volume alone. Encourage useful participation and community quality.

# 12. Photos and File Security

Registered users may upload photos to eligible general discussions and business rooms.

The server must:

- Enforce file-size and image-dimension limits.
- Validate actual file content, not just filename extensions.
- Reject unsupported formats.
- Strip EXIF metadata, especially GPS coordinates and device-specific metadata.
- Resize and re-encode images to safe supported formats.
- Use unique, non-guessable storage keys.
- Store images outside the relational database.
- Use private object storage and appropriately authorized image access.
- Enforce permissions before creating upload authorization.
- Support reporting, removal, and moderation of images.

Prevent executable or arbitrary files from being uploaded as images.

For the lean MVP, implement essential image screening and user reporting. Advanced automated image classification can be added behind a moderation interface without making it a dependency for the entire application.

# 13. Trophies, Medals, and Achievements

Include a small, configurable achievement system for registered users if it fits within the MVP schedule.

Potential achievements include:

- First meaningful contribution.
- Helpful community participation.
- Approved business submission.
- Consistently positive community feedback.

Medals should appear next to usernames and on profiles once earned.

Do not award achievements to guests.

Avoid rewarding spam, repeated low-quality content, or excessive posting. Achievements must be calculated server-side and must not be editable by clients.

If time is limited, deliver a minimal achievement framework and a small initial set rather than building an elaborate gamification system.

# 14. Account Settings and User Controls

Include:

- Username and profile editing.
- Password and email management.
- Radius preferences.
- Favorite locations.
- Blocked-user management.
- Report submission and relevant status visibility.
- Account deletion.
- Terms of Service and privacy policy access.
- Location permission guidance.
- Logout.

Users must be able to withdraw location permission through their device settings. Explain which features stop working when permission is unavailable.

# 15. Monetization and Future Features

Do not launch paid subscriptions, sponsored posts, business advertising, or event promotion in the MVP.

Keep the content model and authorization system flexible enough to add future promotional content with clear labeling.

Future phases may include:

- Following users.
- Direct messaging.
- Events and meetups.
- Event creation, RSVPs, and event moderation.
- Business promotion tools.
- Sponsored content.
- Push notifications.
- More advanced reputation and achievement systems.

Do not build these features now merely because the architecture may eventually support them.

# 16. Database Model

Design a normalized relational schema. Names below are conceptual and may be adjusted to suit the chosen ORM.

Core tables/entities:

- `User`: immutable ID, username, normalized username, email, password hash or authentication reference, birth year, role, account status, timestamps.
- `GuestSession`: internal guest ID, secure session reference, creation and last-activity timestamps, expiration, moderation status.
- `Profile`: user ID, avatar reference, biography, public profile settings.
- `GeneralPost`: author reference, text, creation timestamp, geographic association, status.
- `BusinessPlace`: canonical ID, name, category, address, geographic point, source identifiers, status, attribution.
- `BusinessSubmission`: submitter, proposed place data, review status, decision reason, reviewer, timestamps.
- `BusinessPost`: place ID, author reference, content, creation timestamp, status.
- `Comment`: author reference, parent post or comment, text, creation timestamp, status.
- `Vote`: voter, target content, vote type, timestamp.
- `Photo`: uploader, storage key, target content, moderation status, metadata, timestamps.
- `FavoritePlace`: user ID, place ID, creation timestamp.
- `Achievement`: definition, name, description, display metadata, criteria.
- `UserAchievement`: user ID, achievement ID, awarded timestamp.
- `Report`: reporter, target type and ID, reason, details, status, timestamps.
- `ModerationAction`: target, action, reason, administrator, duration, timestamps.
- `UserBlock`: blocking user, blocked user, creation timestamp.
- `AdminAuditLog`: administrator, action, target, relevant metadata, timestamp.
- `AccountDeletion`: account reference, request and completion timestamps, processing status.
- `AppConfiguration`: configurable limits, radius defaults, and policy settings.

Use explicit relationships, foreign keys, unique constraints, and appropriate indexes.

PostGIS spatial indexes are required for location-based queries. Add indexes for feed pagination, place search, pending submissions, moderation queues, and common authorization lookups.

Use database constraints to prevent duplicate votes, duplicate favorites, and repeated achievement awards.

Do not store uploaded image bytes in PostgreSQL.

Define a clear policy for guest comments that outlive their guest sessions. Preserve the visible GUEST attribution while removing unnecessary guest-session information after its approved retention period.

# 17. API and Security Requirements

Organize the API around explicit resource boundaries.

Expected endpoint groups include:

- Authentication and session management.
- User profiles and settings.
- General feed and comments.
- Business directory and place search.
- Business discussion rooms.
- Favorites.
- Votes.
- Image upload authorization and image records.
- Reports and blocks.
- Guest sessions and expiration.
- Business submissions.
- Achievements.
- Account deletion.
- Administrative moderation.
- Administrative configuration.

For every write endpoint, perform server-side authorization, input validation, rate limiting, and relevant location checks.

Additional requirements:

- Validate request schemas and reject unexpected fields.
- Use parameterized database operations.
- Apply CSRF protection where appropriate for cookie-based web sessions.
- Protect against XSS in user-generated content rendering.
- Restrict CORS to appropriate application origins where applicable.
- Prevent insecure direct object references by checking ownership and permissions.
- Use safe error messages without leaking internal stack traces or sensitive data.
- Keep secrets in environment variables or a secrets manager.
- Never return password hashes, private emails, birth years, internal enforcement notes, or precise location history in public API responses.
- Ensure user-provided content cannot change roles, moderation status, ownership, or database-controlled counters.

# 18. Performance and Abuse Prevention

The app should remain usable as participation increases.

Implement:

- Cursor-based pagination for feeds and large queues.
- Database indexes for geographic and frequently filtered queries.
- Rate limits for registration, login, comments, posts, votes, uploads, reports, and submissions.
- Per-account and, where appropriate, privacy-conscious per-installation abuse controls.
- Configurable limits instead of hard-coded values scattered throughout the application.
- Efficient nearby-place search using PostGIS.
- Idempotent operations where retries could create duplicate records.
- Basic monitoring and structured server logs without unnecessary personal data.

Do not introduce distributed infrastructure before the MVP needs it.

# 20. Acceptance Criteria

The MVP is not complete until the following behaviors are demonstrated by tests or reproducible manual test procedures.

### Location

- A user outside the configured Jacksonville boundary cannot create restricted content or vote.
- A user inside Jacksonville but outside the relevant discussion radius cannot perform restricted actions.
- A valid user within the required radius can participate.
- The server rejects stale, malformed, or insufficiently accurate location readings according to configuration.
- Changing client-side coordinates or user IDs cannot bypass authorization.
- Read-only browsing does not accidentally enable write operations.

### Accounts and guests

- Registered users have unique, persistent identities despite username changes.
- Email addresses and birth years are never exposed through public profiles or APIs.
- Guest accounts cannot create top-level posts, upload photos, access business rooms, or earn achievements.
- Guest accounts expire after 30 days of inactivity.
- Existing guest comments remain attributed to GUEST for one year unless legitimately removed.
- Deleted or banned users cannot continue participating through the same account.
- Account deletion removes the account from public profile views and triggers the documented retention workflow.

### Discussions and voting

- General discussions are distinct from business discussions.
- Business posts are associated with a canonical business record.
- Replies and comments appear under the correct content.
- A user cannot create duplicate votes for the same target.
- Vote totals are computed or maintained securely on the server.
- Pagination works without duplicating or silently skipping ordinary results.

### Business directory and administration

- The initial dataset imports without duplicating records on repeated runs.
- Duplicate submissions are identified or flagged before approval.
- A new submission remains hidden from the public directory until approved.
- An approved submission becomes available in the directory.
- The contributor badge is awarded only after approval.
- Administrators can approve, reject, correct, and merge submissions.
- Administrative actions are recorded in an audit log.
- Non-admin users cannot access administrative functions.

### Moderation and security

- Users can report content and block other users.
- Rate limits are enforced on the server.
- Moderators can remove content and apply suspensions or bans.
- Username changes and new guest sessions do not bypass existing enforcement.
- Images have sensitive metadata stripped before public delivery.
- Unauthorized users cannot retrieve private images or administrative data.
- Automated tests cover critical authorization and location failures.

# 21. Implementation Phases

Work in the following order, reporting what was completed and tested at each phase.

**Phase 1 — Repository and foundation**
- Inspect or initialize the project.
- Configure TypeScript, linting, testing, environment variables, and migrations.
- Set up PostgreSQL and PostGIS.
- Implement initial data models and secure authentication.

**Phase 2 — Location and directory**
- Import Jacksonville boundary data.
- Implement server-side geographic validation.
- Build the business/place directory, search, and favorites.
- Import an initial OpenStreetMap dataset with deduplication and attribution.

**Phase 3 — Core discussions**
- Build the general feed and business rooms.
- Implement posts, comments, replies, voting, and pagination.
- Enforce location eligibility on every relevant write endpoint.

**Phase 4 — Guests and profiles**
- Implement restricted guest sessions and expiration.
- Implement profiles, username changes, settings, and deletion workflows.
- Verify the one-year guest-comment retention behavior.

**Phase 5 — Moderation and administration**
- Implement reporting, blocking, rate limits, strikes, and enforcement.
- Build the admin portal and fast business-submission review queue.
- Add audit logs and moderation history.

**Phase 6 — Photos and achievements**
- Implement secure image upload, metadata stripping, and basic moderation.
- Add the minimal achievement system where feasible.

**Phase 7 — Verification and release readiness**
- Run automated tests and security checks.
- Verify location and authorization bypass attempts.
- Test database migration and recovery procedures.
- Document deployment, configuration, backups, and operational dependencies.
- Provide a clear list of incomplete features and remaining risks.
